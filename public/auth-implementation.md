# 과제 7 · 한걸음 인증 구현 설명서

## ① 무엇으로 붙였나

기존 과제 6의 Vinext·React·Cloudflare D1 앱에 **애플리케이션 세션 인증을 직접 구현**했습니다. 비밀번호 해싱·검증은 **bcryptjs 3.0.3**, bcrypt 비용 인자 **12**에 맡겼습니다. 세션 난수와 SHA-256은 런타임 Web Crypto API를 사용합니다. 인증 전체를 라이브러리에 맡긴 것은 아니며, 가입·세션·접근 제어 로직은 이 프로젝트의 구현입니다.

이어 사용한 T06 최종 커밋: `704893d03fd11c581da6ecc192192a5458679add`. 과제 7은 같은 Git 이력 위에서 수정했습니다. 기존 T06 주소는 그대로 사용합니다. 인증 도입 직전 운영 DB의 계획·할 일·실행 기록 등 6개 테이블이 모두 0건임을 확인했고, 사용자도 입력한 기록이 없다고 확인했습니다. 따라서 계정으로 이전할 운영 자료는 0건입니다. 기존 행이 남아 있는 다른 환경에서는 owner_id가 null인 자료를 공개하거나 첫 가입자에게 임의 배정하지 않습니다.

## ② 왜 이 방법을 골랐나

과제에서 계정별 비밀번호 저장값 비교, 동일 인증 값의 로그아웃 후 거절, A/B 계정 차단을 실제로 보여줘야 합니다. 별도 외부 서비스 계정이나 API 비밀키 없이 기존 D1에서 이를 검증할 수 있는 서버 세션을 선택했습니다. bcryptjs는 별도 네이티브 바이너리 없이 Workers에서 실행할 수 있습니다. 매번 독립적인 salt로 해싱하며, 72바이트 제한을 서버에서 확인해 조용한 잘림을 막습니다. 비밀번호는 12자 이상이어야 합니다.

비교했지만 선택하지 않은 방법: Sites의 ChatGPT 로그인은 플랫폼 계정을 활용하기에는 편하지만, 이 과제의 앱 자체 가입 화면과 비밀번호 해시 DB 증거를 직접 제공하기 어렵습니다. 무효화 목록 없는 JWT는 로그아웃 후 이전 토큰 재사용을 즉시 막기 어려워 선택하지 않았습니다. 자작 해시 알고리즘은 사용하지 않았습니다.

근거: [bcryptjs 공식 문서](https://github.com/dcodeIO/bcrypt.js) — salt 생성·비교 API와 72바이트 제한.

세션은 암호학적 난수 32바이트입니다. 원문은 로그인 성공 시 쿠키에만 전달하며, DB에는 SHA-256 값만 저장합니다. 세션은 발급 후 **24시간**에 만료됩니다. 운영 쿠키는 `__Host-move_session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`를 사용하고 URL에 싣지 않습니다. 로컬 HTTP 미리보기만 별도의 move_session 쿠키를 사용합니다. 로그아웃은 현재 세션을, 비밀번호 변경은 모든 기존 세션을 무효화합니다. 세션 서명 비밀키는 사용하지 않으며, 무작위 세션 원문은 공개 소스·브라우저 JS·제출 기록에 저장하지 않습니다.

요청의 owner_id/user_id/X-User-Id는 인증 근거로 사용하지 않습니다. 실제 계정은 서버가 검증한 세션에서만 얻습니다. 쓰기는 같은 출처의 JSON 요청만 받습니다. 로그인·가입·민감 작업은 계정 및 IP별 15분 단위 횟수 제한을 적용합니다.

## ④ 안 열리는 것을 확인한 기록

`/auth-evidence.json`은 로컬 프로덕션 Worker와 D1에 실제 요청해 생성한 검증 결과입니다. 성공 응답과 거절 응답의 URL·메서드·본문·상태 코드를 포함하며, 비밀번호·쿠키 원문은 마스킹했습니다. 해시 비교의 두 계정은 같은 무작위 비밀번호로 만든 일회용 로컬 테스트 계정이며 테스트 뒤 삭제합니다. 표시된 bcrypt 저장값은 비밀번호 원문이 아닙니다.

확인 범주: 비로그인 접근, 로그아웃·만료·비밀번호 변경 후 세션 거절, A→B 및 B→A 읽기·수정·삭제 차단, URL·헤더·본문의 소유자 위조 방어, 목록·내보내기 격리 및 거절 전후 자료 불변. 반환 상태는 비로그인 401, 타인 자료 404, 교차 출처 403입니다. 파일에 실제 기록이 생성되기 전에는 이 설명만으로 검증 통과를 주장하지 않습니다.

5일 전후 계산의 자동 테스트는 **합성 로컬 fixture**입니다. 본인이 서로 다른 실제 날짜에 사용한 5일 기록의 대체 증거가 아닙니다. 실제 5일 사용은 아직 완료하지 않았습니다.

## ⑤ AI와 나

- AI에게 맡긴 일: 인증·소유권 검사·5일 관찰 화면 구현, DB 변경, 요청/응답 검증과 문서 초안.
- 내가 직접 판단한 일: 운동을 주제로 선택했고 헬스·걷기를 관리하기로 했습니다. 기존 실제 입력 자료가 없음을 확인했습니다. 관찰 질문과 계획 규칙은 앱에서 시작 전에 직접 검토·확정해야 합니다.
- AI 제안을 따르지 않은 일: 현재 대화에서 확인된 사례가 없습니다. 실제 사용 후 거절하거나 수정한 제안이 있으면 그 내용과 이유를 추가합니다. 확인되지 않은 결정을 대신 만들어 쓰지 않았습니다.

## ⑥ 아직 못 막은 것과 한계

- 이메일 소유권 확인·비밀번호 찾기·다중 인증이 없습니다. 비밀번호를 잊으면 스스로 복구할 수 없으며, 비밀번호가 유출되면 추가 인증 없이 계정을 탈취할 수 있습니다.
- 기본 계정/IP 횟수 제한은 있지만, 분산된 IP와 여러 계정을 이용한 대규모 공격 및 서비스 거부를 완전히 막지는 못합니다. 서버 운영 경보·전문적인 감사 로그 체계가 없습니다.
- 세션 원문은 HttpOnly 쿠키로 보호하지만 기기나 브라우저 자체가 장악된 경우까지 보호하지 않습니다. 이미 내려받은 내보내기 파일은 로그아웃·계정 삭제로 회수할 수 없습니다.
- 계정 삭제는 운영 DB에서의 삭제이며 호스팅 업체의 내부 보관·백업 삭제까지 보증하지 않습니다.
- 과거 소스 버전은 Git 이력에 남습니다. 이번 구현에 실제 비밀번호·세션을 커밋하지 않습니다. 이미 공개된 과제 6 기록이 있었다면 인증 추가가 이전 복사본까지 회수할 수는 없습니다. 이 사용자 운영 자료는 도입 당시 0건이었습니다.
- 5일 관찰의 확정 기록은 수정할 수 없습니다. 오입력 방지를 위해 저장 전 확인을 요구합니다. 실수 시 기록의 메모를 제출 설명에 별도로 보충해야 합니다. 5일의 전후 차이만으로 인과관계를 확정하지 않습니다.

## 짧은 확인 방법 4줄

1. 어디로 가나요: 공개 앱 주소의 로그인 화면과 `/source` 안내로 갑니다.
2. 세 단계 안에 무엇을 하나요: ① 직접 가입·로그인 ② 내 계획과 기록 저장 ③ 로그아웃 후 개인 화면 재접속. 계정 간 검증은 설명서와 증거 JSON에서 확인합니다.
3. 무엇이 보이면 통과인가요: 로그인 전에는 자료가 없고, 로그인 후 본인 자료만 보이며, 로그아웃 후 개인 화면은 로그인으로 돌아갑니다. 요청 증거에서 타인 접근이 404이고 자료가 변하지 않습니다.
4. 안 될 때 무엇이 보이나요: 실패 문구와 재시도 안내가 나타나며, 비밀번호·토큰 원문을 제출하지 않습니다. 정상 동작으로 가장하지 않고 오류 상황을 기록합니다.

## 실제 5일 사용 순서

1일차에 질문·지표(하루 실제 운동 시간)·분 단위·계산 규칙·처음 계획 규칙을 확정합니다. 날짜마다 실제 시간을 합산해 기록하고, 실제 운동이 없던 날은 확인 후 0분으로 기록합니다. 미기록은 0분과 다릅니다. 2일차 기록 뒤 3일차 기록 전에 계획 규칙 하나를 변경하고 이유를 씁니다. 나머지 세 날짜에 실제 사용한 뒤 합계·평균을 손계산과 대조하고 전체 내보내기 파일을 제출합니다.
